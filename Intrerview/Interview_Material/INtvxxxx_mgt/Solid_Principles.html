SOLID Principles of Object-Oriented Design

The SOLID principles are a set of guidelines that help software developers create maintainable, scalable, and robust object-oriented systems. These principles were introduced by Robert C. Martin and are considered fundamental to designing clean and efficient code.

1. Single Responsibility Principle (SRP)

Definition: A class should have only one reason to change, meaning it should have only one job or responsibility.

Explanation: Each class should focus on a single task or functionality. This makes the class easier to maintain, understand, and test. If a class has more than one responsibility, changes to one responsibility may affect the other, leading to code that is more difficult to maintain.

Example:

javascript
class User {
    constructor(name, email) {
        this.name = name;
        this.email = email;
    }
}

class UserRepository {
    save(user) {
        // Code to save the user to the database
    }
}

class EmailService {
    sendEmail(user, message) {
        // Code to send an email to the user
    }
}
  • User class handles user data.
  • UserRepository handles database operations.
  • EmailService handles email-related tasks.

2. Open/Closed Principle (OCP)

Definition: Software entities (classes, modules, functions, etc.) should be open for extension but closed for modification.

Explanation: You should be able to add new functionality to a class without changing its existing code. This promotes the use of polymorphism and abstraction to achieve flexibility and maintainability.

Example:

javascript
class Notification {
    send(message) {
        throw new Error('This method should be overridden');
    }
}

class EmailNotification extends Notification {
    send(message) {
        // Send email notification
    }
}

class SMSNotification extends Notification {
    send(message) {
        // Send SMS notification
    }
}

function notifyUser(notification, message) {
    notification.send(message);
}
  • Notification class is open for extension (new notification types) but closed for modification (the base class is not altered).

3. Liskov Substitution Principle (LSP)

Definition: Objects of a superclass should be replaceable with objects of a subclass without affecting the correctness of the program.

Explanation: Derived classes must be substitutable for their base classes. This means that the subclass should enhance the base class behavior without altering its core functionality.

Example:

javascript
class Bird {
    fly() {
        return 'Flying';
    }
}

class Sparrow extends Bird {
    // Inherits fly method
}

class Penguin extends Bird {
    fly() {
        throw new Error('Penguins cannot fly');
    }
}
  • The Penguin class violates the Liskov Substitution Principle because it changes the expected behavior of the fly method.

4. Interface Segregation Principle (ISP)

Definition: A client should not be forced to implement an interface it doesn't use.

Explanation: Instead of creating a large, monolithic interface, create smaller, more specific interfaces. This prevents classes from being forced to implement methods they do not need.

Example:

javascript
class Printer {
    print(document) {
        // Print the document
    }
}

class Scanner {
    scan(document) {
        // Scan the document
    }
}

class MultiFunctionPrinter {
    constructor(printer, scanner) {
        this.printer = printer;
        this.scanner = scanner;
    }

    print(document) {
        this.printer.print(document);
    }

    scan(document) {
        this.scanner.scan(document);
    }
}
  • The MultiFunctionPrinter class can print and scan, but it uses separate interfaces for each task, adhering to the ISP.

5. Dependency Inversion Principle (DIP)

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details. Details should depend on abstractions.

Explanation: Instead of depending on concrete classes, rely on abstractions (interfaces). This makes the system more flexible and easier to modify.

Example:

javascript
class MailService {
    send() {
        // Implementation for sending mail
    }
}

class Notification {
    constructor(mailService) {
        this.mailService = mailService;
    }

    notify() {
        this.mailService.send();
    }
}
  • The Notification class depends on the MailService abstraction, not its implementation. This allows the notification system to be easily extended or modified by swapping out the mail service with another implementation.

Summary

  • SRP: Each class should have one responsibility.
  • OCP: Classes should be open for extension, but closed for modification.
  • LSP: Subclasses should be substitutable for their base classes.
  • ISP: Use small, specific interfaces rather than a single, general-purpose interface.
  • DIP: Depend on abstractions, not concrete implementations.

By following these principles, you can design software that is more modular, easier to understand, and more resilient to change.
